# CUMCM Taste

> 先理解现实，再选择模型。

`cumcm-taste` 是一个面向数学建模 Agent 的事实审查 skill。它让 Agent 在推荐模型或算法之前，先回答三个更基础的问题：

1. 现实中有哪些因素可能改变题目要求的结果？
2. 哪些因素必须进入模型，哪些可以在误差范围内省略？
3. 是否存在阈值、饱和、反转、滞后或其他必须分类讨论的专业效应？

它最初面向全国大学生数学建模竞赛（CUMCM），也适用于工程、物理、环境、生物、经济与运筹等包含真实情境的建模任务。

## 它解决什么问题

常见的错误顺序是：

```text
看到题目 → 想到熟悉的模型 → 把现实塞进模型 → 为结果补解释
```

本项目要求改成：

```text
还原题意 → 调查现实机制 → 判断因素能否省略 → 推演适用条件 → 准许选择模型
```

它既不鼓励把所有现实细节都塞进模型，也不接受“为了好算”而无依据地删除因素。目标是得到**最小但仍然可信的模型**。

## 调用后会发生什么

Agent 必须先生成一份“方法准入报告”，内容包括：

- 题目对象、输入输出和硬约束；
- 题面之外可能有影响的现实因素；
- 每个因素的影响方向、量级和证据；
- 必须保留、验证后决定、可以省略和暂时未知的因素；
- 专业文献中的假设、参数范围和适用条件；
- 阈值、饱和、反转、分段或状态切换等特殊效应；
- 不代入最终数据的公式、量纲、极限与守恒检查；
- 推荐的最小模型、有效范围和升级条件。

这份报告完成前，Agent 不应急着推荐神经网络、优化算法、微分方程或其他方法。

## 一个直观例子

假设题目研究物体运动，空气阻力没有在题面中明确给出。

普通回答可能直接写“忽略空气阻力”。`cumcm-taste` 会要求 Agent 继续检查：

- 速度和尺度处于什么范围？
- 阻力相对重力或驱动力大约有多大？
- 忽略阻力会只改变小数点后的数值，还是会改变方案排名或可行性？
- 经典真空公式的适用条件是否成立？
- 如果阻力不可忽略，采用线性阻力、平方阻力还是分区模型？

只有回答这些问题后，才决定是否把阻力写进主模型。

## 为什么不是只给 Codex 使用

真正的方法写在平台无关的 Markdown 和 JSON Schema 中，不依赖某个 Agent 的专用工具名：

```text
skill/cumcm-taste/
├── SKILL.md                    核心执行流程
├── agents/openai.yaml          Codex/OpenAI 界面元数据
└── references/
    ├── evidence-policy.md      证据等级与文献提取规则
    ├── report-template.md      方法准入报告模板
    └── output-schema.json      结构化输出协议

adapters/generic-agent/
└── INSTRUCTIONS.md             普通 Agent 入口

evals/cases.md                  验收用例与评分标准
```

- 支持 skill 的 Agent 可以安装 `skill/cumcm-taste`。
- 普通 Agent 可以读取 `adapters/generic-agent/INSTRUCTIONS.md`。
- API Agent 可以要求结果符合 `output-schema.json`。
- 没有搜索、计算或 subagent 能力的平台可以降级执行，但必须如实说明能力缺口。

## 在 Codex 中使用

将 `skill/cumcm-taste` 目录复制或链接到 Codex 的 skills 目录，然后调用：

```text
$cumcm-taste 阅读这道题。在选择模型前完成现实因素审查、专业背景研究和方法准入报告。
```

也可以直接提出自然语言请求：

```text
先不要选算法。检查这个现实情景中可能遗漏的边界、约束和专业效应，判断哪些因素必须建模。
```

## 在一般 Agent 中使用

把以下文件和题目一起提供给 Agent：

1. `adapters/generic-agent/INSTRUCTIONS.md`
2. `skill/cumcm-taste/SKILL.md`
3. `skill/cumcm-taste/references/evidence-policy.md`
4. `skill/cumcm-taste/references/report-template.md`

然后要求：

```text
按照 CUMCM Taste 工作流处理本题。在方法准入报告完成以前不要选择建模方法；没有实际使用的搜索、计算或并行研究能力不得声称已经使用。
```

## 并行专业研究

如果 Agent 支持 subagent，它应当让独立研究者在主 Agent 分析场景的同时检索专业资料。研究者接收原始题目和中性任务，不接收主 Agent 偏好的模型或预期结论，避免“先有答案、再找论文”。

研究结果必须分成两部分：

1. 背景、符号、假设、参数范围和适用条件；
2. 与题目直接相关的结论、分类标准、特殊效应及其建模后果。

如果平台没有 subagent，则顺序完成同样的研究，并明确说明它不是独立并行审查。

## 证据底线

- 不编造论文、参数、模拟、独立审查或最优性证明。
- 搜索摘要和普通网页只能提供线索，不能自动支撑强技术结论。
- 引用结论时保留研究情景、假设、参数范围和具体定位。
- 找不到可靠证据时写“尚未解决”，不能用常识填平缺口。
- 缩小可行域后，除非证明保留原问题的全部可行解，否则不得声称全局最优。

## 如何验收

仓库中的 `evals/cases.md` 提供四类测试：物理简化、机制切换、简单问题和证据不足。一个合格版本应当做到：

- 不在事实审查完成前抢先选方法；
- 不把所有可能因素机械地加入模型；
- 能解释每个省略项为什么可省略；
- 能发现需要分类讨论的阈值和特殊效应；
- 能承认工具、资料和结论的边界；
- 给出最小可行模型，而不是最长的模型。

验收的不是报告长度，而是 Agent 是否因此少犯“脱离事实”和“无依据简化”这两类错误。

## 当前边界

这是首个可执行版本，暂不包含 MCP 服务、自动检索器或特定学科知识库。核心流程在不同 Agent 上稳定之后，再根据实际失败案例添加适配器或工具，避免一开始把方法论做成沉重框架。
